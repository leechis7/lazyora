# 개발과 릴리스

[한국어](development.md) | [English](en/development.md)

`main`은 릴리스용 브랜치, `dev`는 다음 버전의 개발 내용을 통합하는 브랜치입니다. 기능·버그 수정·문서 작업은 `dev`에서 분기합니다. 커밋과 GitHub 업로드는 사용자의 명시적인 승인 후 진행합니다.

소스 빌드 방법과 호환성·검증 기록은 [빌드와 검증](build.md)을 참고하세요.

## Jira 칸반 운영

2026-10-27부터 스프린트 없이 칸반으로 운영합니다. 기한을 임의로 정하거나 새 스프린트를 만들지 않고, 백로그 우선순위에 따라 `할 일 → 진행 중 → 검토 → 완료`로 관리합니다. 기존 스프린트 1·2 이력은 보존하며 스프린트 2는 종료했습니다.

한 번에 한 일감을 진행합니다. 실제 착수 시 `진행 중`, 구현과 필요한 검증을 마치면 근거와 남은 CI·게시 여부를 댓글로 남기고 `검토`로 전환합니다. 사용자가 검토 완료를 명시하면 `완료`로 전환합니다. 수정 요청은 `진행 중`으로 되돌리고 재검증 후 다시 `검토`로 올립니다. Jira에 검토 상태가 아직 없으면 진행 중을 유지하고 댓글로 검토 대기를 명시하며 완료로 대신 처리하지 않습니다. 미구현 하위 작업이 남은 에픽은 완료하지 않습니다. Tuivory 공개 패키지처럼 선행 의존성이 준비되지 않았으면 `할 일`에 두고 사유를 기록합니다. 커밋·게시 승인과 일감별 순차 브랜치 운영은 그대로 유지합니다.

팀 관리형 Jira 보드에서는 프로젝트 설정(현재 UI의 공간 설정) → 기능 → 스프린트를 끄면 스프린트 없는 운영으로 전환할 수 있습니다. 현재 연결 도구로는 이 기능 토글을 변경할 수 없어 UI 설정 확인이 남아 있으며, 운영 규칙 변경과 Jira 화면 설정 완료는 구분합니다. [Atlassian 공식 절차](https://support.atlassian.com/jira-software-cloud/docs/enable-sprints/)

## 기능 개발

먼저 Jira 관련 일감을 확인하고, 없으면 사용자 승인 후 등록합니다. 작업 브랜치에는 Jira 번호와 주제를 넣습니다.

```bash
git switch dev
git pull --ff-only origin dev
git switch -c feature/LORA-17-schema-browser
```

로컬 개발·검증의 기본 빌드는 `make build`로 Linux ARM64 하나만 생성합니다. 다른 OS/아키텍처의 로컬 바이너리는 사용자가 요청할 때만 개별 타깃으로 만듭니다. GitHub CI·Release는 `make build-all`로 전체 지원 대상을 빌드합니다.

개발 및 로컬 검증 후 승인받아 한국어 메시지로 커밋하고 브랜치를 게시합니다. `dev` 대상 PR을 만들면 CI가 실행됩니다. 테스트·vet·Linux/Windows/macOS AMD64·ARM64 빌드가 통과한 뒤 PR을 병합하고, `dev` 푸시에서도 통합 검증을 수행합니다. 병합 후 끝난 feature 브랜치는 정리합니다.

CI에서 만든 바이너리는 실행 결과의 `binaries` 아티팩트에서 7일 동안 받을 수 있습니다. GitHub 아티팩트 다운로드 시 실행 권한이 사라졌다면 `chmod +x`를 적용합니다. CI에는 실DB·구형 커널 검증이 포함되지 않으므로 Oracle·CentOS 시험은 별도로 진행합니다.

Windows·macOS 실행기에서는 대소문자가 다른 사용자 지정 설정명으로 설정·프로필·암호 파일을 실제 생성·갱신하여 서로 덮어쓰지 않는지도 검사합니다. 이 검사는 실제 TUI·Oracle 접속 검증을 대신하지 않습니다.

macOS 설정 경로 검사는 `macos-15-intel`에서 실행합니다. CPU와 무관한 파일명 충돌 검사이며, ARM 실행기의 용량 부족 대기 지연을 줄이기 위해 실행기 풀을 고정합니다. macOS AMD64·ARM64 실행파일은 별도 전체 빌드 단계에서 모두 검증합니다.

## 승인된 일괄 검증의 예외 절차

다음은 2026-10-21에 승인된 백로그 묶음의 예외이며 모든 신규 작업에 자동 적용하지 않습니다. 해당 묶음의 백로그는 일감별 로컬 구현·검증·커밋·로컬 `dev` 병합·브랜치 정리까지 마친 뒤 다음 일감으로 진행합니다. 중간 GitHub 게시·PR·CI 실행과 대기를 생략하고, 전체 구현 후 통합 PR로 GitHub 검증을 진행합니다. 이미 실행 중인 CI는 그대로 둡니다. 워크플로 자체를 비활성화하지 않으며, 게시 전 로컬 `dev`의 미게시 커밋을 원격 상태로 덮어쓰지 않습니다.

당시에는 구현·필요한 검증이 끝난 일감을 근거 댓글과 함께 `완료`로 전환했지만, 2026-10-27부터는 위 칸반 운영의 `검토` 단계를 거쳐 사용자 검토 완료 후에만 `완료`로 전환합니다. 일괄 검증 기간에는 로컬 검증 결과와 GitHub 통합 CI 대기를 구분해 기록합니다. 미구현 작업이나 하위 작업이 남은 에픽은 완료 처리하지 않습니다.

## 릴리스

신규 기능이 포함된 릴리스는 **minor**를 올리고 patch를 0으로 초기화합니다(예: `0.6.0 → 0.7.0`). 버그 수정만 포함하면 **patch**를 올립니다(예: `0.6.0 → 0.6.1`). `0.x` 버전에도 같은 원칙을 적용합니다. 사용자가 릴리스 버전을 명시하면 그 지정을 따릅니다.

**major는 제품 버전으로 사용자만 결정합니다.** 에이전트는 기능 개수·제품 완성도·호환성 변경을 이유로 major를 임의로 올리지 않습니다. 사용자의 명시적인 major 변경 지시 전까지 현재 major를 유지하며, `0.9.0` 다음 기능 릴리스는 `0.10.0`입니다.

1. `dev`에서 릴리스 준비용 feature 브랜치를 만들고 `internal/appinfo/info.go`와 `README.md`·`README.en.md`의 버전을 함께 갱신합니다. CHANGELOG의 `Unreleased` 변경을 해당 버전과 날짜로 옮기고 비교 링크도 갱신합니다. `docs/releases/vX.Y.Z.md`와 대응 영문 설명에 기능·단축키 변경·다운로드·지원 범위를 적고 한국어 본문에 영어 섹션 또는 링크를 함께 제공합니다. Release Actions는 해당 한국어 파일이 있으면 이를 릴리스 본문으로 사용합니다. 버전 태그는 `vX.Y.Z` 형식으로 사용합니다.
2. 변경을 `dev`로 병합하고 `dev → main` PR을 생성합니다.
3. CI 통과와 필요한 실환경 시험을 확인한 뒤 사용자 승인으로 `main`에 병합합니다. `dev → main` 병합은 merge commit을 사용하여 두 브랜치의 커밋 관계를 유지합니다.
4. 사용자 릴리스 요청 후 아래와 같이 해당 `main` 커밋에 태그를 붙여 게시합니다. 아래 버전 번호는 예시입니다.

```bash
git switch main
git pull --ff-only origin main
git tag -a v0.0.2 -m 'v0.0.2 릴리스'
git push origin v0.0.2
```

Release Actions는 태그와 소스 버전의 일치 여부 및 태그 커밋의 `main` 포함 여부를 확인하고 테스트·vet·Linux/Windows/macOS 빌드를 수행합니다. 성공하면 Linux AMD64/ARM64 실행파일과 Windows AMD64/ARM64 `.exe`와 macOS AMD64/ARM64 실행파일, LICENSE, README.md, SHA256SUMS를 첨부한 정식 GitHub Release를 발행합니다. `main` 병합만으로 릴리스를 발행하지 않습니다. 기존 태그와 릴리스는 덮어쓰지 않습니다.

릴리스 후 `main`의 merge commit 또는 긴급 수정이 `dev`에도 포함되도록 `main → dev`를 merge commit으로 동기화합니다. 정상 릴리스 시 `dev → main` PR을 squash/rebase 방식으로 병합하지 않습니다.

## 자동화 설정

SQL 구문 색상은 tview v0.42.0의 로컬 렌더링 확장을 사용합니다. [원본과 변경 범위](../third_party/tview/README.lazyora.md)를 확인하세요. 의존성 갱신 시 원본과 다른 Go 파일은 textarea.go 하나여야 하며, 렌더링 회귀 검사를 함께 수행합니다. 릴리스에는 MIT 라이선스 고지를 TVIEW-LICENSE.txt로 첨부합니다.

- `.github/workflows/ci.yml`: `dev`·`main` 대상 PR 및 두 브랜치 푸시 검증
- `.github/workflows/release.yml`: 버전 태그 푸시 시 정식 릴리스 발행
- CI·Release의 Go 버전은 `mise.toml`과 함께 갱신합니다.
- CI·Release의 Go 모듈 다운로드는 일시적인 네트워크 오류에 대비해 최대 3회 재시도합니다. 실제 테스트·vet·빌드는 실패를 그대로 보고합니다.
- 외부 Actions는 커밋 SHA로 고정합니다. 버전 변경 시 SHA와 주석을 함께 갱신합니다.

GitHub에서 CI 성공을 병합의 필수 조건으로 강제하려면 `dev`와 `main`에 브랜치 규칙을 설정하고 `Test, vet and build` 검사를 필수로 지정합니다. 워크플로 파일만으로 병합이 차단되지는 않습니다.

현재 브랜치의 구현·검증·사용자 검토와 승인된 커밋·병합·정리를 마친 뒤 다음 브랜치를 시작합니다. 사용자 명시적 전환 지시가 없으면 승인 대기 중에도 다른 브랜치로 이동하지 않습니다.

## Tuivory 스타일 가이드 반영

Tuivory 자체 개발은 별도 프로젝트에서 진행합니다. 정식 v0.11.2는 `github.com/leechis7/tuivory/go v0.2.0`을 포함합니다. 개발 의존성과 공통 UI 우선 원칙은 아래 항목을 따릅니다. LazyOra에서는 공개 Go 스타일 패키지를 import하고, 검토한 버전의 변경을 LORA 일감에서 적용·검증합니다. Tuivory 소스를 복사하거나 로컬 경로로 replace하지 않습니다. 출처 커밋, 변경 원칙, LazyOra 적용 위치, 검증과 보류 사유는 [반영 기록](tuivory-sync.md)에 남깁니다. 공통 가이드와 Oracle/Toad 관련 제품 동작을 구분하며 커밋·게시·릴리스 승인은 기존 절차를 따릅니다.


## 한국어·영어 문서 유지

앞으로 문서를 새로 작성하거나 수정할 때는 한국어와 영어를 함께 작성·갱신합니다. README·사용/개발 안내·릴리스 설명 등 대응 문서의 내용·버전·명령·단축키·검증 범위와 언어 전환 링크를 맞춥니다.

기본 문서는 한국어 `README.md`이며 해외 사용자는 `README.en.md`에서 시작합니다. 영문 핵심 안내는 `docs/en/`, 앱과 공유하는 영문 사용 가이드는 `docs/guide.en.md`에 있습니다. 언어별 진입 링크를 유지하고 설치·지원 대상·단축키·암호 관리·사용 동작이 바뀌면 대응하는 한국어/영어 문서를 함께 갱신합니다. 릴리스 준비 시 두 README의 버전을 확인합니다. 과거 감사·성능 측정·개발 이력의 전체 번역을 요구하지는 않으며, 영문 안내에서도 실제 검증과 모의 화면/교차 빌드의 범위를 구분합니다.


문서만 게시할 때도 dev 대상 PR과 CI를 거쳐 main에 통합해야 기본 README에서 보입니다. 앱 동작/버전 변경이 없는 문서 정리는 기존 태그·릴리스·바이너리를 다시 만들지 않습니다. 내장 가이드 원문 변경은 다음 빌드부터 적용됩니다. [문서 색인](index.md)에서 현행 안내와 보관 기록을 구분하세요.

## 공통 UI는 Tuivory 우선

공통 그리기·테두리/겹침 보호·컨트롤·스타일은 공개 Tuivory API를 먼저 확인해 사용합니다. 같은 결함을 LazyOra와 Tuivory에 별도로 고치지 않습니다. 공통 API가 없으면 별도 Tuivory 프로젝트에서 제공할 범위를 정하고, 제공 후 LazyOra에서 어댑터로 연결합니다. Oracle 실행·트랜잭션·탭/작업공간의 데이터 소유권·명령과 언어/ASCII 선호 정책은 제품 책임입니다. tview 위젯은 Tuivory Styler로 스타일을 적용하며, 새 모델/위젯으로 옮길 때 기존 입력·포커스·팝업 차단·복사·데이터 안전을 검증합니다.

현재 공개 `github.com/leechis7/tuivory/go v0.2.0`(태그 `go/v0.2.0`, 커밋 `987d1a6786033a6bf063235b5e7fea7b565f0af0`)을 고정합니다. 팝업 전체는 `WideSafeScreen`, 폼/버튼 등의 제한 폭 라벨은 `CellText`에 위임합니다. 로컬 `popupFill`은 제거했습니다. v0.11.2에 포함되며 기존 v0.11.1 자산은 v0.1.0을 유지합니다. [적용·보류 검토](audits/lora-76-tuivory.md)를 참고하세요.
