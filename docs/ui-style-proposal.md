2026-10-23 · LORA-69 · v0.10.0 기준 조사·설계안

이 문서는 최초 조사·설계안을 보존한 자료입니다. 후속 사용자 승인으로 공통 스타일의 로컬 적용을 진행했으며, 현행 동작은 [UI 스타일 규칙](ui-style.md)과 [구현·검증 기록](audits/lora-69-implementation.md)을 기준으로 확인하세요. 키맵은 변경하지 않았습니다. 현행 [UI 스타일 규칙](ui-style.md)을 기반으로, 기존 [색상 조사](audits/lora-69.md)에서 확인한 문제를 공통 토큰·컴포넌트·검증 규칙으로 해결하는 것이 목적입니다.

## 1. 조사 결과와 채택 방향

TUI에도 공식 스타일링 자료가 있습니다. 다만 이번에 확인한 자료는 라이브러리별 테마·스타일 API와 사례가 중심이며, 모든 TUI에 적용되는 단일 디자인 표준으로 보기는 어렵습니다. 따라서 TUI의 색상·셀 제약은 해당 자료에서, 상태·키보드·대비 원칙은 일반 UI 지침에서 참고합니다.

| 공식 자료 | 확인한 설계 방식 | LazyOra 적용 판단 |
| --- | --- | --- |
| [Textual 테마 가이드](https://textual.textualize.io/guide/design/) | 테마 변수와 컴포넌트별 변수, 배경을 고려하는 글자색, 실행 중 테마 변경 | 화면은 색상 값 대신 의미별 토큰을 참조하고, 본문·보조·비활성 글자색을 분리 |
| [Lip Gloss 공식 문서](https://github.com/charmbracelet/lipgloss#advanced-color-usage) | 테마와 단말 색상 프로필에 맞는 색 정의 및 명시적 프로필별 색 선택 | ANSI 8/16과 256/RGB를 분리해 해석하는 구조 참고. tview/tcell은 유지 |
| [Ratatui 색상 예제](https://www.ratatui.rs/examples/style/colors/) | 기본색·인덱스 색·RGB 색을 실제 위젯에서 비교 | 앱의 공통 컴포넌트를 한 화면에서 비교하는 견본과 회귀 자료 유지 |
| [Carbon 색상 지침](https://www.carbondesignsystem.com/building-blocks/foundations/color/guidelines), [토큰 목록](https://www.carbondesignsystem.com/building-blocks/foundations/color/tokens) | 테마와 레이어에 맞는 역할별 토큰, 입력·테두리·상태의 연계 | 본문과 입력창, 팝업, 제목의 전경/배경을 한 쌍으로 관리 |
| [DTCG 2025.10 형식](https://www.designtokens.org/tr/2025.10/format/) | 이름·타입·별칭을 갖는 토큰 교환 형식 | 기본색 → 의미 → 컴포넌트 별칭 구조 참고. 초기 구현은 Go 자료형으로 충분하며 JSON 로더는 도입하지 않음 |
| [WAI 키보드 지침](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/) | 컴포넌트 간 이동과 내부 이동 분리, 포커스와 선택 구분 | Tab/Shift+Tab은 영역 간, 방향키는 목록 내부. 포커스와 선택을 독립적으로 표시 |
| [WAI 모달 지침](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) | 모달 내부 포커스 순환, 배경 입력 차단, 닫은 뒤 포커스 복귀 | 팝업 공통 컨테이너와 이벤트 처리 계약으로 적용 |
| [W3C 색 사용](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html), [대비 설명](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) | 색만으로 의미를 전달하지 않기, 일반 텍스트 대비 4.5:1 및 예외 | 텍스트·표식·선 모양을 함께 사용. 대비 수치는 단말 참조 팔레트의 조사 기준으로 채택 |
| [xterm 공식 문서](https://www.invisible-island.net/xterm/manpage/xterm.html) | `boldColors`에 따라 굵은 기본 전경색이 밝은색으로 변할 수 있음 | ANSI의 읽기 쉬운 색 조합과 굵기 속성을 별도로 검증 |

위 자료의 웹 접근성 API나 CSS 자체가 터미널에 존재하는 것은 아닙니다. 여기서는 설계 원칙을 차용하며, ARIA 지원·WCAG 적합성·스크린 리더 호환성을 보장한다는 뜻은 아닙니다. DTCG 자료도 W3C Recommendation은 아닌 Community Group 보고서입니다. Lip Gloss의 오래된 AdaptiveColor 예제를 그대로 도입하거나 별도 라이브러리가 stdin을 조회하도록 만들지 않습니다.

## 2. 공통 구조

스타일 해석 입력은 **테마 × 색상 프로필 × 컴포넌트 역할 × 상태 × 배경 역할**입니다. 테마와 단말 능력을 같은 변수로 취급하지 않습니다.

```text
사용자 테마(dark / light / blackwhite) + tcell 단말 능력
    → 프로필(ANSI8 / ANSI16 / Indexed256 / TrueColor)
    → 기본 팔레트
    → 의미별 전경·배경 토큰
    → 컴포넌트 + 상태 스타일
    → tcell.Style / 테두리 / 상태 표식
```

색을 사용하는 규칙은 다음과 같습니다.

- 원시 RGB·ANSI 인덱스는 팔레트 정의에만 둡니다. 화면 코드의 `SetTextColor(ColorWhite)` 같은 지정은 공통 스타일 호출로 옮깁니다.
- 글자색과 배경색은 한 쌍으로 정합니다. 제목·힌트도 자신이 실제로 그려지는 배경을 사용합니다.
- 같은 색상 값을 가진 두 토큰도 역할은 유지합니다. 흑백에서 본문과 강조가 같은 흰색이어도 테마 복원 시 서로 다른 토큰으로 해석합니다.
- 읽기 전용 Form 설명은 `text.body/surface.dialog`이며 `field.text/field.background`가 아닙니다.
- 테마 변경은 토큰으로 스타일만 다시 적용합니다. 입력값·SQL·암호·탭·선택·스크롤·작업자·트랜잭션 상태를 초기화하거나 페이지를 재생성하지 않습니다.
- 스타일 적용 순서에 의존하지 않게 합니다. 같은 상태에 같은 스타일을 여러 번 적용해도 결과가 같아야 합니다.

권장 의미별 토큰은 다음과 같습니다. 이름은 설계용이며 실제 Go 이름은 구현 시 일관되게 정합니다.

| 토큰 묶음 | 의미 |
| --- | --- |
| `surface.canvas / panel / dialog / editor / field / menu / footer` | 그려지는 영역의 배경 |
| `text.body / hint / disabled / onField / onSelection` | 해당 배경에서 읽을 글자색 |
| `border.normal / focus / divider`, `title` | 영역 경계·포커스·제목 |
| `selection.active / inactive`, `cursor` | 현재 선택과 입력 위치 |
| `button.normal / focus / disabled / destructive` | 버튼 상태. 포커스와 기본 동작은 별도 정보 |
| `status.info / success / warning / error / busy` | 실행 결과·주의·오류·처리 중 |
| `grid.header / current / range / edited / null` | 결과 그리드의 독립된 의미 |
| `sql.keyword / identifier / string / number / comment / bind / error` | SQL 문법 역할 |

## 3. 색상 수와 테마 정책

| 프로필 | 규칙 |
| --- | --- |
| ANSI8 | 인덱스 0~7만 사용. 보조 글자색과 본문색이 같아도 허용하며 간격·표식으로 계층 구분 |
| ANSI16 | 인덱스 0~15 명시. 8색과 비슷한 큰 면적을 유지하고 밝은색은 필요한 강조에 제한 |
| Indexed256 | ANSI 0~15의 사용자 변경 영향을 줄이도록 주요 면적에 16~255 인덱스를 명시 |
| TrueColor | RGB를 명시. 256색과 역할·정보 계층은 같고 색의 정밀도만 달라짐 |
| 흑백 테마 | 각 단말 프로필 안에서 검정/밝은 중립색만 사용. 색상 프로필이 아니라 사용자 테마이며 모든 상태에 문자·선 표시 제공 |

현재 `limitedColors` 하나로 8/16을 합친 부분을 프로필 열거형으로 구분할 계획입니다. 사용자 테마는 자동 단말 배경 감지로 덮어쓰지 않습니다. 지원 능력은 tcell이 제공하는 정보를 우선 사용하고, TERM 이름만으로 마우스·입력 키·True Color를 추정하지 않습니다. `TERM` 미설정의 기존 fallback과 터미널 호환 처리는 별도 기능으로 유지합니다.

ANSI 색 번호는 고정 RGB가 아닙니다. 흰색/검정이라는 이름도 사용자 팔레트에 따라 달라집니다. 문서의 대비는 tcell 참조 팔레트 기준이며 실제 단말에서 다시 확인해야 합니다. 프로그램이 사용자의 ANSI 팔레트를 변경하지 않습니다.

### 3.1 초기 색상 후보

[프로필·역할별 후보 CSV](ui-style-palette-candidate.csv)에 **12개 프로필 × 16개 핵심 역할 = 192개 전경/배경 쌍**을 명시했습니다. 이는 제품 설정 파일이나 최종 시각 승인 결과가 아닌 검토용 후보입니다. 숫자는 ANSI/256색 인덱스이며 `#` 값은 RGB입니다.

| 테마/프로필 | 기본 글자/배경 | 입력 글자/배경 | 선택 글자/배경 | 수정 셀 글자/배경 |
| --- | --- | --- | --- | --- |
| 다크 8 | 7 / 0 | 0 / 7 | 7 / 4 | 0 / 3 |
| 다크 16 | 7 / 0 | 0 / 7 | 15 / 4 | 0 / 3 |
| 라이트 8 | 0 / 7 | 0 / 7 | 7 / 4 | 0 / 3 |
| 라이트 16 | 0 / 15 | 0 / 15 | 15 / 4 | 0 / 3 |
| 다크 256 | 252 / 236 | 235 / 254 | 255 / 24 | 0 / 180 |
| 라이트 256 | 235 / 255 | 235 / 231 | 231 / 24 | 0 / 180 |
| 다크 RGB | #eceff4 / #2e3440 | #202a36 / #eceff4 | #ffffff / #005f87 | #202a36 / #d7af87 |
| 라이트 RGB | #202a36 / #f3f5f7 | #202a36 / #ffffff | #ffffff / #005f87 | #202a36 / #d7af87 |
| 흑백 8/16/256/RGB | 7 / 0 | 0 / 7 | 0 / 7 | 7 / 0 ＋ `*` |

8색에서 3은 어두운 노랑/올리브, 4는 남색, 7은 밝은 회색에 해당하는 참조값입니다. 라이트 8색은 입력 배경과 일반 배경이 같아질 수 있으므로 입력 영역 표시를 필수로 합니다. 흑백은 미커밋 상태를 배경색 차이 없이 `*`로 표시합니다.

후보의 일반 텍스트·포커스 경계 192쌍은 **굵기 없음**으로 계산했을 때 참조 팔레트 대비 최저 4.936:1입니다. 이 수치는 전체 앱·SQL 토큰·팝업 합성·커서까지 검증했다는 뜻은 아닙니다. `font_weight=none`을 코드에서 임의로 Bold로 덮으면 후보의 대비 검증은 무효가 됩니다. 특히 검정 전경의 입력·버튼·선택·수정 셀에는 ANSI Bold를 기본 적용하지 않습니다.

라이트 편집기는 RGB #ffffff, 256색 231, 16색 15, 8색 7로 유지합니다. 배경을 회색으로 바꿔 문법색 문제를 해결하지 않습니다.

### 3.2 문법 강조와 의미 색

8색에서는 모든 토큰에 서로 다른 색을 부여하는 것을 목표로 하지 않습니다. 읽기 쉬운 제한된 색과 문법 구조를 우선합니다.

| 역할 | 다크 ANSI8 | 라이트 ANSI8 | 16/256/RGB | 흑백 |
| --- | --- | --- | --- | --- |
| 일반 식별자 | 본문 | 본문 | 편집기 본문 | 본문 |
| 키워드 | 7, 필요한 경우 밑줄 | 4, 필요한 경우 밑줄 | 정보/키워드 전용 토큰 | 본문, 필요한 경우 밑줄 |
| 문자열 | 7 | 0 | success 계열에서 편집기 배경 대비를 확인한 색 | 본문 |
| 숫자 | 7 | 0 | 별도 토큰. 대비 부족하면 본문 | 본문 |
| 주석 | 7, Dim 사용 안 함 | 0, Dim 사용 안 함 | 읽을 수 있는 hint 토큰 | 본문 |
| 바인드 | 3, 굵기 없음 | 1, 굵기 없음 | warning 계열, 밝은 노랑/흰색 조합 금지 | 본문 ＋ 선택적 밑줄 |

문법 색은 바탕색과 한 쌍으로 따로 검증합니다. 일반 경고 색을 편집기의 다른 배경에 검증 없이 재사용하지 않습니다. SQL 원문 자체에 컬러 마크업을 삽입하지 않고 현재 하이라이터의 표시 계층을 유지합니다.

## 4. 상태와 공통 컴포넌트

포커스는 ‘다음 키 입력을 받을 곳’, 선택은 ‘사용자가 고른 항목’, 수정됨은 ‘커밋되지 않은 변경’입니다. 서로 합치지 않습니다. 이는 WAI 키보드 지침의 구분을 TUI에 적용한 설계 판단입니다.

| 상태 | 공통 표시 | 색만으로 판단하지 않게 하는 방법 |
| --- | --- | --- |
| 영역 포커스 | 이중선 테두리와 대비가 강한 경계 | `╔═╗`/`╚═╝`; 지원 제한 시 ASCII 경계와 포커스 표식 |
| 선택 | 선택 전경/배경 쌍 | 현재 행/항목의 `>` 또는 활성 탭 표시 |
| 비포커스 선택 | 선택 기억 유지, 포커스 이중선 제거 | ‘선택됨’과 ‘현재 조작 영역’을 구분 |
| 미커밋 셀 | edited 배경 | `*`, 행 표시 또는 선택 셀 상세의 ‘미커밋’ |
| 오류 | error 전경 | ‘오류:’/오류 코드와 해결에 필요한 문구 |
| 경고 | warning 전경 | ‘주의:’와 영향 설명 |
| 비활성 | disabled 스타일, 동작 차단 | 필요한 경우 ‘사용 불가’와 이유. 문구를 배경색으로 숨기지 않음 |
| 실행 중 | busy 상태 | ‘실행 중’, 진행 수치, 취소 가능 여부 |

상태가 겹칠 때는 **편집 중 입력 커서 → 현재 셀/선택 범위 → 미커밋 배경 → 줄무늬/일반 배경** 순으로 시각 스타일을 적용합니다. 선택이 미커밋 배경을 덮더라도 `*`와 상태 설명은 유지합니다. 오류는 문구와 표식을 추가하되 선택의 글자색만 빨강으로 덮어 대비를 깨지 않습니다.

### 입력·선택·버튼

- 입력 필드는 라벨과 밝은 입력 면, 선택박스는 같은 면에 `▾`를 항상 표시합니다. 제한 폰트에는 `v`를 사용합니다. 비밀번호는 마스킹하되 라벨은 유지합니다.
- 8색 라이트처럼 배경만으로 구분하기 어려운 경우 필드 경계·밑줄 또는 양끝 표식 중 공통 구현 하나를 채택합니다. 입력과 선택의 구분은 화살표로 유지합니다.
- 선택 목록은 펼쳐진 영역 전체를 불투명하게 칠하고, 한글 2셀 문자의 경계까지 정리합니다. 화면 밖이면 위로 펼치거나 높이를 제한합니다.
- 버튼은 `[ 저장 ]`, `[ 취소 ]`처럼 공통 외형을 사용하고 현재 포커스를 별도 표식/밑줄로 표시합니다. 버튼 그룹 좌우 이동과 Tab 이동을 지원합니다.
- 기본 버튼과 현재 포커스는 별개입니다. 스타일 개선을 이유로 Enter 동작을 바꾸지 않습니다. 기존 ‘변경 미리보기는 진행이 기본’ 사용자 결정도 유지합니다. 위험 SQL·종료 확인의 기존 기본 동작도 별도로 보존합니다.
- 안내문은 form 설명 전용 스타일을 쓰며 입력 라벨·힌트·오류를 각각 구분합니다.

### 패널·메뉴·그리드

- SQL·결과·스키마 패널은 동일한 포커스 규칙을 씁니다. 기존 제한 색상 SQL 파랑/결과 청록은 역할 식별에 참고하되, 글자·제목·포커스를 그 색 하나로 표현하지 않습니다. 어두운 배경에서 파랑의 대비가 부족하면 비포커스 장식만 유지하고 포커스와 제목은 고대비 토큰을 사용합니다.
- 메뉴의 빈칸·글자 뒤 배경·구분선은 모두 menu surface로 칠합니다. 일반 메뉴는 단일 테두리이며, 사용자가 요청한 이중선은 실제 포커스가 있는 패널/팝업 영역에 적용합니다. 메뉴 항목마다 상자를 만들지 않습니다.
- 구분선은 기능 그룹 사이에만 놓고 선택/클릭 대상에서 제외합니다. 하위 메뉴 있음은 `>`로 표시합니다. 좌우 최상위 메뉴 이동과 하위 메뉴 복귀 계약은 기존 동작을 유지합니다.
- 그리드 헤더는 별도 배경과 구분선, 현재 셀은 선택 스타일, 범위는 범위 스타일을 사용합니다. 줄무늬는 장식이므로 8색·흑백에서는 생략할 수 있습니다.
- NULL은 문자열 ‘NULL’과 구분되는 표시·상세 정보를 유지하며 Dim만으로 표현하지 않습니다. 실제 ROWID 숨김·복사·편집 동작은 색상 설계와 독립적으로 보존합니다.
- 하단은 현재 조작 가능한 단축키만 표시합니다. 팝업 열림/패널 크기 조절 중에는 해당 상태의 안내만 표시해 중복을 방지합니다.

### 팝업과 간격

팝업은 modal인지 단순 메뉴/드롭다운인지 구분합니다. 아래 규칙은 모달에 적용합니다.

| 항목 | 제안 기준 |
| --- | --- |
| 카드 내부 여백 | 좌우 2셀, 위아래 1행 |
| 라벨과 필드 | 최소 1셀, 한글 표시 너비로 정렬 |
| 일반 폼 행 | 1행 필드 + 1행 간격을 기본으로 하되 작은 창에서 간격 먼저 축소 |
| 섹션 간격 | 1행, 필요 시 짧은 섹션 제목 |
| 버튼 간격 | 최소 2셀, 폼과 버튼 사이 1행 |
| 메뉴 | 위아래 0~1행, 항목 좌우 1셀; 불필요한 중첩 테두리 금지 |
| 작은 창 | 여백 축소 → 내용 스크롤 순서. 확인/취소 조작을 항상 접근 가능하게 유지 |

셀 간격 수치는 LazyOra 제안이며 외부 표준에서 정한 값은 아닙니다. 웹의 px를 그대로 옮기지 않습니다. 권장 정상 화면은 100×30 이상으로 검토하고, 80×24와 60×18에서도 내용/버튼이 겹치지 않는지 확인합니다. 더 작은 창은 안내와 복구 경로를 제공합니다.

모달 내부는 빈칸과 여백까지 불투명하게 칠합니다. 뒤 화면은 입력을 받지 않으며, 바깥 클릭으로 자동 확정하거나 닫지 않습니다. Tab은 모달 내부에서 순환하고 Esc는 현재 단계만 취소합니다. 드롭다운이 열려 있으면 먼저 닫고, 직접 편집이면 입력을 취소한 뒤 부모 팝업을 닫습니다. 닫은 뒤 호출 지점으로 포커스를 돌려줍니다. 실행 중 취소 불가 단계 등은 기존 작업 제약을 유지하며 이유를 표시합니다.

## 5. 코드에 적용하는 구체적 순서

기존 Go + tview/tcell을 유지합니다. 아래 이름과 코드는 **설계 예시**로 현재 구현된 API가 아닙니다.

```go
type Profile uint8 // ANSI8, ANSI16, Indexed256, TrueColor

type StylePair struct {
    Foreground tcell.Color
    Background tcell.Color
}

type WidgetState struct {
    Focused, Selected, Disabled, Edited, Invalid bool
}

// theme/profile/role/background/state만으로 결과를 결정한다.
func ResolveStyle(theme ThemeID, profile Profile,
    role ComponentRole, surface SurfaceRole, state WidgetState) WidgetStyle
```

`WidgetStyle`은 `tcell.Style` 외에 테두리 종류와 표식을 포함할 수 있습니다. 초기에는 string 키를 런타임에 찾는 거대한 CSS 엔진보다 Go 열거형·자료형으로 누락을 확인하는 편이 적절합니다. 표식 적용이 데이터 자체를 바꾸어 복사/내보내기에 섞이지 않도록 표시 계층에 둡니다.

| 단계 | 현재 코드 | 변경 목표 | 완료 기준 |
| --- | --- | --- | --- |
| A | `app.go`, `theme.go` | 색상 프로필 분리, 의미별 쌍과 공통 컴포넌트 역할 정의 | 12조합 후보와 실제 해석 결과 일치, 토큰 누락 없음 |
| B | `widgets.go`, `theme.go`, `choice.go`, `form_popup.go` | 폼 설명·제목·선택·버튼·드롭다운·불투명 모달 통일 | 암호 안내/복사 제목 재현 해소, 클릭/키 이동 유지 |
| C | `grid.go`, `grid_inline.go`, `sql_colors.go`, `menu.go`, `menu_groups.go` | 그리드 상태 조합·SQL 토큰·메뉴 상태를 공통 역할에 연결 | 수정 셀과 선택 동시 식별, 복사·마우스·키맵 회귀 없음 |
| D | `theme_apply.go` 및 탭/팝업 생성부 | 색상 값 치환 제거, 역할별 재적용 | 초기 테마와 왕복 뒤 같은 역할·색상. 입력·스크롤·선택 보존 |
| E | `theme_audit_test.go`, 기존 화면 테스트 | 견본·상태별 검증과 실제 터미널 비교 | 아래 검증 항목을 기록하고 실제 사용자 단말에서 확인 |

A~D는 하나의 스타일 통합 작업을 단계별로 진행하는 계획입니다. 제품 수정 승인 뒤 현재 브랜치 정리와 저장소 규칙에 맞춰 구현 범위를 확정합니다. 후속 적용은 기존 LORA-69 브랜치에서 진행했으며 신규 라이브러리를 도입하지 않았습니다. 커밋·게시 승인은 별도로 받습니다.

## 6. 검증 기준과 예상 작업량

1. 텍스트 전경/배경의 참조 대비 4.5:1 이상을 목표로 합니다. 포커스 경계는 내부 목표 3:1 이상과 이중선/표식으로 평가합니다. 비활성 항목도 읽을 수 있게 하되 WCAG 인증이라고 표현하지 않습니다.
2. 8/16색은 Bold가 글꼴만 바꾸는 경우와 밝은색으로 바꾸는 경우를 둘 다 확인합니다. Dim은 필수 정보·NULL·안내문에 사용하지 않습니다.
3. 테마를 dark → light → blackwhite → 원래 테마로 바꾸고, 동적 텍스트를 제외한 역할별 스타일이 초기와 같아야 합니다. 현재의 단순 프레임 차이 개수만으로 성공/실패를 판정하지 않습니다.
4. 67개 기존 장면과 새 공통 견본을 12조합·한영으로 캡처합니다. 크기 128×40 / 100×30 / 80×24 / 60×18에서 겹침·말줄임 원문 접근·버튼 접근을 확인합니다.
5. 실제 SecureCRT·MobaXterm과 일반 xterm 호환 단말에서 확인합니다. TERM·tcell 색상 수·실제 팔레트·굵게 설정을 함께 기록합니다. 시뮬레이션 통과와 실제 단말 통과는 별도로 기록합니다.
6. 폼 저장/취소, 메뉴 좌우, 마우스 선택, 그리드 복사·미커밋 표시, 팝업 닫기, 숨겨진 SQL 탭/작업 공간, 테마 변경 중 입력 유지 등 실제 상태 전이를 검증합니다.

기존 추정 3~5일은 주요 결함 수정 중심입니다. 이 문서의 **공통 스타일 구조 정비와 전체 컴포넌트 이관까지 포함하면 약 4~7일**로 계획하는 편이 적절합니다. 단말 환경 확보·발견되는 예외 수에 따라 달라지는 개발 계획용 추정입니다. A/B와 암호 안내·제목 결함을 먼저 처리하고, C/D 이후 전체 회귀를 수행하면 검토 단위를 작게 유지할 수 있습니다.
